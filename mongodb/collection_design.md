# MongoDB design

Database: `energy_consumption`. Three collections. Sample documents are in
[sample_documents.json](sample_documents.json).

## Collections

### `dataset_sources`
One document per imported file. Same information as the MySQL table of the same name.

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. Other collections point to it. |
| `name`, `description`, `source_url`, `original_filename` | string | |
| `timezone_note` | string | How to read the timestamps. |
| `imported_at` | Date | |

### `energy_readings`
One document per one-minute reading.

| Field | Type | Notes |
|---|---|---|
| `_id` | ObjectId | Generated by MongoDB. |
| `source_id` | ObjectId | The `_id` of the source document. |
| `timestamp` | Date (BSON) | See "Timestamps" below. |
| `measurements` | subdocument | The seven values: `global_active_power`, `global_reactive_power`, `voltage`, `global_intensity`, `sub_metering_1`, `sub_metering_2`, `sub_metering_3`. |

### `forecast_results`
One document per forecasting run, for Task 4. It stays empty until a real model
has been run. Shape only (the angle brackets are types, not values):

```text
{
  source_id:  <ObjectId>,
  model_name: <string>,
  target:     <string, e.g. "global_active_power">,
  run_at:     <Date>,
  metrics:    { rmse: <number or null>, mae: <number or null> },
  parameters: { ... model settings ... },
  predictions: [ { timestamp: <Date>, value: <number> }, ... ]
}
```

MySQL splits runs and predictions into two tables. Here the predictions are
embedded in the run document, because they are always read together with their
run and a forecast horizon is short. If a run ever had a very large number of
predictions (the limit is 16 MB per document), they should move to their own collection.

## Why this structure

- **Measurements in a subdocument.** The seven values belong together, and
  `measurements.voltage` reads naturally in queries. A new measurement can be
  added without changing the top-level shape.
- **One document per minute** (not one per day). It matches the MySQL rows 1:1,
  which makes the two databases easy to compare, and queries stay simple.
- **Separate source collection** (not copied into every reading) so source
  details are stored once. Readings only hold a small `source_id`.
- MongoDB fits here because readings are self-contained documents, we do not
  need joins for the main queries, and fields can be added later without a
  schema migration. It is not a claim that MongoDB is faster than MySQL;
  we have not measured that.

## Missing values

The file marks missing data with `?`. In MySQL these become `NULL`. In MongoDB
they become an explicit `null` inside `measurements`, so every reading has the
same seven fields, just like the MySQL columns. They are **not** replaced with 0.
`$avg` ignores `null`, so averages are not distorted. A query on
`{"measurements.voltage": null}` matches both `null` and absent fields.

## Timestamps

The file has local date and time with no time zone. MongoDB's `Date` type is
always UTC. We store the local clock time **as if it were UTC**: the line
`16/12/2006;17:24:00` becomes `ISODate("2006-12-16T17:24:00Z")`. The `Z` does
not mean the household was in UTC; it is a storage convention so the value
matches the MySQL `DATETIME` `2006-12-16 17:24:00` exactly. Do not convert these
values to another time zone.

## Regular collection or time-series collection?

MongoDB 8.0.34 (installed here) supports time-series collections, which store
measurements compactly. I created a temporary one to test it: MongoDB rejected
a unique index with `Unique indexes are not supported on time-series collections`.
A regular collection accepted it.

| | Regular collection | Time-series collection |
|---|---|---|
| Unique `(source_id, timestamp)` | Yes | No (tested) |
| Safe to rerun the importer | Yes, duplicates are rejected | No built-in protection |
| Same behavior as the MySQL design | Yes | Partly |
| Storage and speed tuning for time data | Standard | Built for it |

**Decision: a regular collection.** The unique index lets the importer be
rerun without creating duplicate readings, which is a requirement and matches
the MySQL `UNIQUE (source_id, timestamp)`. The cost is that we do not get the
time-series optimizations. For 2 million rows this is acceptable, and this is
the simpler option to explain.

## Indexes

| Collection | Index | Reason |
|---|---|---|
| `energy_readings` | `{source_id: 1, timestamp: 1}`, **unique** | Prevents duplicates, and serves date-range queries for one source and "latest N" queries (the index can be read in reverse). |
| `energy_readings` | `{timestamp: 1}` | Date queries that do not filter by source. Mirrors `idx_measurement_time` in MySQL. |
| `dataset_sources` | `{name: 1, original_filename: 1}`, **unique** | Lets the importer find or create a source without duplicating it. Mirrors the MySQL unique constraint. |
| `forecast_results` | `{source_id: 1, run_at: -1}` | List the runs for a source, newest first. |

The indexes are created by `mongodb/setup_indexes.py` in Step 7. Nothing has been
created in MongoDB yet. This step is design only.
